<objective>
Step (5) of the roadmap's strict internal order, and the last step of the phase: split the Studio's post list into two language-filtered lists so English and Farsi siblings are managed as distinct editorial surfaces.

Purpose: close roadmap success criterion 4's Studio half and finish CONTENT-01.
Output: a rewritten `src/sanity/structure.ts`, matching assertions in the check script, and the phase's end-of-phase human verification.

**Why the Studio duplicates the language predicate on purpose.** CONTENT-02 says the filter is expressed in exactly one place, and it is: `EN_LANGUAGE` in `src/sanity/lib/queries.ts` owns every public READ path. The Studio's list filters are editorial chrome, not a read path that any visitor can reach, and the structure builder cannot import a GROQ fragment meant for the content client without dragging server-read concerns into Studio config. The duplication is deliberate and bounded to two string literals in one file, and the check script pins the allowed set of files to exactly those two so a third occurrence anywhere fails the gate. Record this reasoning in the SUMMARY so a future reader does not "fix" it.

**Why the English list is tolerant and the Farsi list is strict.** After plan 02-04 every existing post carries an explicit English value, so tolerant and strict are equivalent today. They stop being equivalent the moment a future writer creates a post without the stamp. With a tolerant English filter such a document is still visible and editable; with a strict one it would be invisible in both lists, which is the worst outcome available. Farsi is always explicit by design, so the Farsi filter is a plain equality (research Open Question 3).

**On the list titles.** D-05 fixes the wording as "Posts — English" and "Posts — Farsi". These are Studio UI labels chosen by Saeid, not English prose, so the project's no-em-dash content rule is not being violated by using his literal wording. If he prefers, "Posts (English)" and "Posts (Farsi)" is a two-token change; the check script deliberately asserts only that each title contains the language word, so swapping the separator does not break the gate.
</objective>

<hard_constraints>
1. **NEVER run `npm run build`.** The build gate is `npx next build`.
2. **Run no package-manager install command.** `package.json` and `package-lock.json` must be byte-unchanged.
3. **Do not add a dependency.** `sanity/structure` ships with the installed `sanity@4.22.0`.
4. **A custom filter on a document type list REPLACES the preset type filter, it does not append to it.** Verified in the installed source: the builder presets a type filter and a matching param, and calling the filter method overwrites it. Every custom filter written in this plan must restate the post type clause itself, or the list will show every document type in the dataset.
5. **Both lists need explicit distinct ids.** The builder defaults a document type list's id to the type name, so two post lists would both default to the same id and collide in Studio pane state and in the URL.
6. **Every filtered list needs an explicit api version.** Serialising a document list whose filter differs from the preset emits a console warning otherwise, and the warning says it will become required.
7. **Do not mix quoting styles in `src/sanity/structure.ts`.** The current file is Sanity CLI boilerplate using single quotes and no semicolons, which is inconsistent with every other file under `src/sanity/`. Since this rewrite touches nearly every line, convert the WHOLE file to the repo's dominant style: double quotes and semicolons. Do not leave a half-converted file.
8. **Do not change the trailing spread** that lists every other document type. It already excludes posts, categories and authors, so the split does not double-list posts.
9. `npx tsc --noEmit` must exit 0 and the lint gate must pass.
10. **No AI attribution in commits.**
