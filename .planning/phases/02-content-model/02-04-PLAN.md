<objective>
Step (4) of the roadmap's strict internal order: stamp `language: "en"` on every pre-existing post, in both datasets, behind a dry-run-by-default gate.

Purpose: satisfy roadmap success criterion 3 and complete CONTENT-01. Until this runs, the tolerant D-03 filter is what keeps existing posts visible; after it runs, English is explicit in the data and the Studio's language lists are complete.
Output: `scripts/migrate-post-language.ts`, a `--post-migration` mode on the check script, a stamped dev dataset, and a stamped production dataset once Saeid gives the go.

**Which dataset does success criterion 3 mean?** Both, with production as the gating one (research Open Question 4). There are two datasets with different contents: production `blog_posts` holds 26 posts, dev `blog_posts_dev` holds 17. `.env.local` points at the DEV dataset, so running the migration the obvious way stamps 17 dev documents, zero production documents, and prints a confident success message. That is research Pitfall 6, and it is the single most likely way this plan produces a false pass. Every run in this plan names its dataset out loud, and the production run uses `--env-file .env.vercel-prod`.

**Why dry run is the default and not a flag.** D-09 fixes it: the script reports first, mutates only under `--execute`, and the production mutation waits for Saeid's explicit in-session go. Two mechanisms reinforce each other, the flag and a server-side validated commit that persists nothing. The patch itself is a set-if-missing, so it is additive, idempotent and re-runnable, and it can never overwrite a value the Phase 3 pipeline wrote.
</objective>
