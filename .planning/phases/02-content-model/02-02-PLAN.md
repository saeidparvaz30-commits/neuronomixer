<objective>
Step (2) of the roadmap's strict internal order: express the English-language filter exactly once and interpolate it into every public post query, then prove mechanically that the change is inert and that step (1) was textually faithful.

This plan closes CONTENT-02. It adds `EN_LANGUAGE` to `src/sanity/lib/queries.ts` and creates `scripts/checks/language-filter.check.ts`, the phase's verification harness, which later plans extend.

Purpose: after this plan lands, no Farsi document can ever surface on an English public surface, and the phase's hard ordering invariant is satisfied at the code level.
Output: one new exported constant, 12 interpolation sites, and a check script with an offline mode and a `--live` mode.

**Ordering invariant, stated in deploy terms (research Pitfall 7).** "The filter is live before the first Farsi document exists" is satisfied at merge time by this plan, because Phase 3 is what creates the first Farsi document. But statically generated and ISR pages keep serving pre-filter HTML until the production build is regenerated (`revalidate` is 3600 on the post page, 60 on the author page, 30 on the homepage, and the sitemap plus static params are build-time artifacts). The real precondition for Phase 3 is therefore "filter deployed to production AND the production build regenerated", not "filter merged". Deploying is outside this phase and gated on Saeid, so this plan records the invariant as a handoff obligation in its SUMMARY rather than performing it. Margin is comfortable: Phase 3 lands Farsi documents as drafts, and the Sanity client already runs on a published perspective, so drafts cannot reach a public read regardless.

**Why there is no stored query-baseline.json.** 02-RESEARCH.md's Wave 0 gap list suggests capturing a pre-change result-set snapshot to a JSON artifact. This plan uses two stronger, staleness-free substitutes instead: the parity assertion runs both variants of each query in the SAME process against the same dataset, so nothing can drift between capture and compare, and the git fidelity assertion diffs the relocated query TEXT against the recorded pre-extraction ref, which no result-set snapshot could do. This is a validation-approach choice inside Claude's discretion, not a reduction in coverage. Both behaviours the baseline would have covered are covered.
</objective>
