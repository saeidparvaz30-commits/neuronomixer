<objective>
Attach the model half of the pipeline to the CLI front end: the subscription-CLI transport, the translate pass, the code-side structural gate, the verify pass, the `translationNotes` rendering, the draft write, and the usage record.

Purpose: this is where PIPE-01 and PIPE-02 are actually satisfied. Everything protective was built first, so this plan's job is to drive the two passes over the subscription CLI correctly, one post at a time (D-16), refuse to write when the gate says no, and put the result somewhere Saeid reviews rather than somewhere readers see.
Output: a script that turns an approved English post into a reviewable Farsi draft.
</objective>

    Build one transport helper the whole file uses. `callClaude(prompt: string)` spawns `claude -p --model sonnet --output-format json` as a child process and writes the entire prompt to stdin, which sidesteps Windows command-line length limits and quoting. Both passes use these two helpers and nothing else talks to the model.

    Build two module-level constants so every request in a run carries byte-identical instruction text: `GLOSSARY_BLOCK` from `serializeGlossaryBlock(loadGlossary())`, and `TRANSLATE_INSTRUCTIONS`, a fixed instruction text with no per-post interpolation. Do not pass the glossary through a CLI argument; a multi-line Farsi-laden block on a Windows command line is exactly the quoting hazard stdin exists to avoid.

State that em dashes are an English-prose rule and do not apply to the Farsi output.

    The per-post payload is `JSON.stringify({ slug, count, strings })` where `strings` is the field items followed by the body items, in that fixed order, and `count` is `strings.length`. There is no request-level schema enforcement on this transport; the count demand lives in the prompt, and the count check in code (already built in `applyTranslatables`) is the gate that decides.

    Run the working set strictly sequentially, one post at a time: translate call, then the Task 2 gate, then the Task 2 verify call, then the Task 3 write, before the next post starts. After every per-post transition, update that post's status in the run-state artifact from plan 03-07 (for example pending, translated, gate-blocked, verified, written, failed) and rewrite the artifact, so a crash or a mid-run subscription usage-limit stop leaves an accurate, resumable record and never a half-written draft.

Without `--resume`, a rerun is already safe because D-08 sibling selection skips translated posts.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| post body to model | Saeid's published prose is sent to Anthropic through the local Claude Code CLI on the subscription, and the output is written back into the content store |
| model response to Sanity | Untrusted generated text becomes document fields, including SEO metadata a search engine will index |
| pipeline to publish-scheduled cron | A document's status field decides whether an unfiltered cron auto-approves it and emails every subscriber |
| script to Postgres | Spend rows are written with a foreign key to a real user |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-03 | Elevation of Privilege | Farsi document status versus the unfiltered publish-scheduled cron | critical | mitigate | The draft carries the literal draft status; the value the cron matches on appears nowhere in the file and an acceptance criterion greps the whole source for it; the document is created under a `drafts.` id, and the cron's client uses the default published perspective so it structurally cannot see a draft; plan 03-09 adds a live count assertion that no Farsi document carries that status on either dataset |
| T-03-02 | Tampering | Portable Text structure | high | mitigate | The fingerprint captured before the model saw the document is compared against the reassembled body before any write; a mismatch blocks that post, reports loudly and lets the run continue |
| T-03-19 | Tampering | injected or altered URLs | high | mitigate | `markDefs` are never enumerated as translatable and are therefore never sent to the model; the fingerprint compares them byte for byte; the verify pass additionally reports URL drift as a finding |
| T-03-05 | Tampering | prompt injection through post body content | medium | mitigate | The model receives an array of strings, the prompt demands exactly the same count back, and the code-side count check before write is the hard gate; anything else fails at the gate. Sources are Saeid's own reviewed content, so the residual risk is low and structurally contained. Do not relax the count gate |
| T-03-06 | Tampering | response to post mismatch | low | mitigate | Calls run strictly sequentially, one post at a time, and each response is consumed inside that post's own iteration; no cross-post result matching exists to get wrong |
| T-03-12 | Tampering | clobbering a hand-edited Farsi draft | medium | mitigate | `createIfNotExists` is the only default write verb; `createOrReplace` appears nowhere; `--retranslate` patches a named field set and leaves the rest, including `_createdAt`, intact |
| T-03-08 | Tampering | `TokenUsage` foreign key violation losing the spend record | medium | mitigate | The ADMIN id is resolved before any spend, the write is awaited with no `.catch`, and a documented fallback writes the rows to the run artifact when the database cannot be reached |
| T-03-07 | Denial of Service | subscription throttling and usage limits | medium | mitigate | Strictly sequential per-post calls with the `--all` brake from plan 03-07; per-post run-state transitions are written after every step, so a mid-run usage-limit stop leaves resumable state and no partial draft write, and a resumed run repeats no completed post (`--resume` plus D-08 sibling skip) |
| T-03-04 | Information Disclosure | run artifacts and console output | high | mitigate | Artifacts carry ids, labels, counts, fingerprints and token totals only; no key, no database URL and no env value is printed or persisted; CLI stderr is never persisted into artifacts |
| T-03-29 | Tampering | truncated translation reaching the gate | medium | mitigate | A truncated response fails `JSON.parse` in `callClaudeJson` and is retried once, and a parseable-but-short one fails the code-side count check before any write; either way the post fails loudly and nothing is written |
| T-03-32 | Tampering | CLI stderr noise parsed as data | low | mitigate | Only stdout is parsed; stderr, which may carry permission-rule notices, is captured solely to print on a non-zero exit and never enters the JSON path or the artifacts |
