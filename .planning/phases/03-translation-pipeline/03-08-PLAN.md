<objective>
Attach the paid half of the pipeline to the CLI: the translate pass, the code-side structural gate, the verify pass, the `translationNotes` rendering, the draft write, and the spend record.

Purpose: this is where PIPE-01 and PIPE-02 are actually satisfied. Everything protective was built first, so this plan's job is to call two batches correctly, refuse to write when the gate says no, and put the result somewhere Saeid reviews rather than somewhere readers see.
Output: a script that turns an approved English post into a reviewable Farsi draft.
</objective>

    - A response whose stop_reason is max_tokens fails that post loudly and does not reach the gate
    - Results are looked up by custom_id, and a run whose results arrive in reverse order still assigns every translation to the right post

  <action>
    Import `Anthropic from "@anthropic-ai/sdk"` and construct the client with `apiKey: process.env.ANTHROPIC_API_KEY`. Abort with a named message when the key is absent and the mode is execute; a dry run must keep working without it.

    Build two module-level constants so the cached prefix is byte-stable across every request in the run: `GLOSSARY_BLOCK` from `serializeGlossaryBlock(loadGlossary())`, and `TRANSLATE_INSTRUCTIONS`, a fixed instruction text with no per-post interpolation. Any per-post data belongs in `messages`, never in `system`, because caching is a prefix match and one changed byte invalidates everything behind it.

    `TRANSLATE_INSTRUCTIONS` must state: return the same number of strings in the same order; translate into natural Farsi technical prose for a professional audience; preserve every number, date, URL, product name and entity name exactly; follow the glossary block above and, for terms not in it, follow common Farsi tech-press usage and keep English in Latin script where that is the norm (D-04); render `metaDescription` under 160 characters where possible because the schema warns above that; and introduce no reference to the United States, America or Israel, which is a standing content rule for this catalog. State that em dashes are an English-prose rule and do not apply to the Farsi output.

    Build one batch request per post. `custom_id` is `${slug}::translate` when that is at most 64 characters, otherwise `${first 16 hex of a sha256 of the slug}::translate`. Record the custom_id to slug mapping in the run-state artifact so a resumed run can match results either way.

    Request params: `model: "claude-sonnet-5"` with no date suffix; `max_tokens: 32000`; `system` as an array of two `TextBlockParam`s where block 0 is `GLOSSARY_BLOCK` with `cache_control: { type: "ephemeral", ttl: "1h" }` and block 1 is `TRANSLATE_INSTRUCTIONS`; `messages` as a single user turn whose content is `JSON.stringify({ slug, strings })` where `strings` is the field items followed by the body items, in that fixed order; and `output_config: { format: { type: "json_schema", schema } }` where the schema is an object with `additionalProperties: false`, required `strings`, and `strings` an array of strings with `minItems` and `maxItems` both pinned to the exact count for that post. Pinning both bounds is the A6 mitigation: a length mismatch becomes an API-level constraint rather than a runtime surprise.

    Send nothing else. Do not set `temperature`, `top_p`, `top_k` or `budget_tokens`, and do not add an assistant turn to force JSON. All of those are removed on Sonnet 5 and return HTTP 400, and a translation script is exactly where an engineer reaches for a zero sampling temperature.

    Create the batch, print its id and status, and persist the batch id into the run-state artifact immediately, before polling. Results stay retrievable for 29 days, so a crashed run resumes with `--resume <batch-id>` rather than paying twice.

    Poll `messages.batches.retrieve` every 30 seconds until `processing_status === "ended"`, printing elapsed time and `request_counts` on each poll so a long run is never silent.

    Stream `messages.batches.results` and build a `Map<string, Message>` keyed by `custom_id`. Never key by array position: the API does not guarantee ordering and the SDK says so in its own doc comment. For each result that is not `succeeded`, print the custom_id and the error and mark that post failed. For each success, assert `stop_reason` is not `max_tokens` and fail that post loudly if it is. Accumulate `input_tokens`, `output_tokens`, `cache_read_input_tokens` and `cache_creation_input_tokens` per post. Print the run's observed cache read total and the resulting hit rate as a measured number, with a line noting that batch requests spread over time so the hit rate is opportunistic even at a one hour ttl.

    Implement `--resume <batch-id>`: skip creation, load the run state from the artifact, and enter the poll and collect path directly.

    Split each post's returned `strings` array back into its field part and its body part using the counts captured in plan 03-07, in the same fields-then-body order the request used. Rebuild the body with `applyTranslatables(source.body, translatedBodyTexts)`, which deep clones and assigns only into the enumerated slots.

    Then run the D-05 tier 1 gate: compare `structuralFingerprint(translatedBody)` against the source fingerprint captured before any model saw the document. On a mismatch, refuse to create the draft for that post, print a loud report naming the slug and the first differing offset, write both fingerprints to the run-state artifact for inspection, and continue with the remaining posts. Code decides whether a draft may be written; the model never gates itself. This should be impossible to fail, which is exactly why it is checked.

    Parse the model response with `JSON.parse` on the response's text block. Do not strip markdown fences: `output_config.format` constrains the output shape, and the fence-stripping in the CV extract route predates structured outputs and is not a pattern to carry forward.

    Build the verify batch from the posts that passed the gate. One request per post, `custom_id` `${slug}::verify` under the same length rule as the translate pass. Same model, same two-block system array with the same cached glossary block, and a `VERIFY_INSTRUCTIONS` block explaining the job: given aligned English and Farsi string pairs, report drift in numbers, dates, URLs, entity and product names, code content, glossary adherence and untranslated leftovers. State the D-04 nuance explicitly: a term left in Latin script is a finding only when it reads as an accidental leftover, not when Latin script is the idiomatic Farsi rendering. State that every `summary` must be one English line with no em dash.

    The user content is `JSON.stringify({ slug, pairs })` where each pair carries the item `label` from the walker, the English text and the Farsi text, so the model's `location` values can be real locations rather than guesses.

    Constrain the response with `output_config: { format: { type: "json_schema", schema: VERIFY_SCHEMA } }` where `VERIFY_SCHEMA` is an object with `additionalProperties: false`, required `findings`, and `findings` an array of objects each requiring `category`, `severity`, `location` and `summary`, with `category` enumerating exactly the seven values in the `Finding` type and `severity` enumerating `info` and `warn`. Import the `Finding` type from `scripts/lib/translation-notes.ts` rather than redeclaring the union, so the schema and the formatter can never disagree. Leave `output_config.effort` unset; it defaults to high, which is what a drift check wants.

    Poll and collect exactly as the translate pass does, keyed by `custom_id`. Render each post's findings with `formatNotes(findings, todayIso())`. When a post's verify request errored or its response failed to parse, set the notes to a single line stating the verify pass did not complete for this post and naming the batch id, and still write the draft. Verify findings never block: that is D-05 tier 2.

    Accumulate the verify pass usage separately from the translate pass usage so the two can be recorded as distinct activities.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| post body to model | Saeid's published prose is sent to a third-party inference API and its output is written back into the content store |
| model response to Sanity | Untrusted generated text becomes document fields, including SEO metadata a search engine will index |
| pipeline to publish-scheduled cron | A document's status field decides whether an unfiltered cron auto-approves it and emails every subscriber |
| script to Postgres | Spend rows are written with a foreign key to a real user |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-03 | Elevation of Privilege | Farsi document status versus the unfiltered publish-scheduled cron | critical | mitigate | The draft carries the literal draft status; the value the cron matches on appears nowhere in the file and an acceptance criterion greps the whole source for it; the document is created under a `drafts.` id, and the cron's client uses the default published perspective so it structurally cannot see a draft; plan 03-09 adds a live count assertion that no Farsi document carries that status on either dataset |
| T-03-02 | Tampering | Portable Text structure | high | mitigate | The fingerprint captured before the model saw the document is compared against the reassembled body before any write; a mismatch blocks that post, reports loudly and lets the run continue |
| T-03-19 | Tampering | injected or altered URLs | high | mitigate | `markDefs` are never enumerated as translatable and are therefore never sent to the model; the fingerprint compares them byte for byte; the verify pass additionally reports URL drift as a finding |
| T-03-05 | Tampering | prompt injection through post body content | medium | mitigate | The model receives an array of strings and is schema-constrained to return exactly the same count, with `minItems` and `maxItems` both pinned; anything else fails at the API or at the gate. Sources are Saeid's own reviewed content, so the residual risk is low and structurally contained. Do not relax the pinned bounds |
| T-03-06 | Tampering | batch result mismatch across posts | medium | mitigate | Results are collected into a Map keyed by `custom_id`; the custom_id to slug mapping is persisted in the run-state artifact; array position is never used |
| T-03-12 | Tampering | clobbering a hand-edited Farsi draft | medium | mitigate | `createIfNotExists` is the only default write verb; `createOrReplace` appears nowhere; `--retranslate` patches a named field set and leaves the rest, including `_createdAt`, intact |
| T-03-08 | Tampering | `TokenUsage` foreign key violation losing the spend record | medium | mitigate | The ADMIN id is resolved before any spend, the write is awaited with no `.catch`, and a documented fallback writes the rows to the run artifact when the database cannot be reached |
| T-03-07 | Denial of Service | token overspend | medium | mitigate | Two sequential batches rather than an interleaved retry storm, a cost estimate printed before submission, `--resume` so a crashed run does not pay twice, and the `--all` brake from plan 03-07 |
| T-03-04 | Information Disclosure | run artifacts and console output | high | mitigate | Artifacts carry ids, labels, counts, fingerprints and token totals only; no key, no database URL and no env value is printed or persisted |
| T-03-29 | Tampering | truncated translation reaching the gate | medium | mitigate | Every successful response is asserted to have a `stop_reason` other than max_tokens; `max_tokens` is 32000 against a largest post of roughly 33k characters of translatable text |
</threat_model>
